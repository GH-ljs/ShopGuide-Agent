# 项目亮点与创新点

建议最终展示控制在 3 条以内。这里按“和普通 RAG 问答方案相比有什么不同”来组织。

## 亮点 1：可信导购 RAG，不让模型自由编造商品事实

普通 RAG 项目常见做法是检索几条文本后直接交给 LLM 生成回答，容易出现商品、价格、优惠、库存和功效被模型补全的问题。

本项目采用受控导购链路：

```text
LLM Plan / 规则解析
-> 后端 Validator
-> 商品硬过滤
-> 向量排序
-> 同一批候选生成回答、商品卡片和对比卡
```

创新点：

- LLM 只负责理解和表达，不直接决定最终商品集合。
- 后端强制校验预算、排除词、序号指代和对比范围。
- 回答文本、商品卡片、详情页和对比卡都绑定同一批 `productId`。
- 无结果时明确说明商品库没有满足条件的商品，不硬凑推荐。

评审价值：

这解决了电商导购里最核心的可信问题：AI 不能编造商品和价格。

## 亮点 2：多轮决策型 Agent，而不是一次性商品搜索

普通商品搜索只解决“找几个商品”，但真实导购更重要的是持续追问和帮助用户做取舍。

本项目支持：

- “不要超过200”“再便宜点”“太便宜了”等预算追问。
- “第二款怎么样”“第三款呢”等序号指代。
- “第二款和第三款对比一下”“哪个更清爽”等对比后决策。
- 同一会话中多个需求隔离，例如先聊笔记本，再聊防晒，再回到笔记本。

关键设计：

- `referenceProducts` 保存当前需求候选。
- `comparisonProducts` 保存最近对比范围。
- `needs[]` 保存多个购物需求，避免不同品类互相污染。
- 对比追问只在被点名或最近对比过的商品中决策，不重新全库召回。

评审价值：

这让项目从“RAG 商品搜索”升级为“能记忆、能比较、能决策的导购 Agent”。

## 亮点 3：评审模式证据链，让推荐过程可解释、可验真

很多 AI Demo 看起来能回答，但评委很难判断它到底有没有真的检索、有没有按约束过滤、有没有偷偷编造。

本项目新增评审模式：

- `/api/chat` 返回 `review` SSE 事件。
- `/api/debug/retrieve` 返回 `review` 字段。

`review` 会展示：

- 用户意图：新搜索、追问、指代、对比或边界问题。
- 硬过滤：类目、商品类型、预算、排除词、偏好。
- 检索过程：检索范围、候选数量、最终返回数量。
- 商品证据：每个商品使用的字段、命中关键词、排序理由。
- 安全边界：禁止编造库存、优惠、销量、活动和未出现的功效。

评审价值：

这让项目具备“可解释 RAG”的比赛展示点。评委不仅能看到结果，还能看到系统为什么这样推荐，以及它如何约束模型不越界。

## 一句话总结

ShopGuide Agent 的创新点不是多接了一个模型，而是把电商导购拆成可控、可验证、可多轮决策的 Agent 链路：

```text
可信事实边界 + 多轮决策记忆 + 评审模式证据链
```

## 工程体验补充：客户端虚拟列表滚动

除了后端 RAG 链路，客户端也针对长对话体验做了性能优化：

- 聊天消息使用 Compose `LazyColumn` 虚拟列表，只渲染可视区域附近的消息项。
- 消息项使用稳定 key 和 `contentType`，减少长会话滚动和流式更新时的无效重组。
- 商品卡片使用 `LazyRow` 横向虚拟列表，并通过 `productId` 保持卡片身份稳定。
- 底部锚点独立成轻量 item，保证长回复和商品卡片插入后仍能准确滚到底部。

这个点可以作为工程质量加分项展示：项目不仅关注 AI 推荐效果，也考虑了真实移动端长会话场景下的滚动性能和交互稳定性。
