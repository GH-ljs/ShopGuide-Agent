# 演示视频脚本

建议录制 5-10 分钟。目标不是把所有功能都点一遍，而是让评委快速理解：这是一个有事实边界、能多轮决策、能解释依据的可信导购 Agent。

## 0. 视频结构

```text
0:00 - 0:40 项目定位
0:40 - 1:30 系统架构
1:30 - 3:20 基础推荐 + 商品卡片 + 详情页
3:20 - 4:10 预算硬过滤
4:10 - 5:40 商品对比 + 决策追问
5:40 - 6:50 跨需求记忆 + 边界处理
6:50 - 8:10 评审模式证据链
8:00 - 9:00 工程质量与测试
9:00 - 10:00 总结亮点
```

## 1. 开场介绍

讲解词：

```text
大家好，这是 ShopGuide Agent，一个基于 RAG 的电商智能导购 Agent。
它不是普通的商品搜索，也不是单纯把检索结果塞给大模型，而是强调可信导购：
商品、价格、卡片、对比结果必须来自商品库，模型不能自由编造。
```

屏幕展示：

- README 或 Android 首页。
- 后端服务已启动。

## 2. 系统架构

讲解词：

```text
整体链路是 Android 原生客户端到 Node.js 后端。
后端先做意图解析和多轮记忆，再执行商品检索、硬过滤和排序。
商品标题、详情、规格、FAQ 和用户评价会被整理成可检索文本，再通过 Embedding 模型转成向量。
向量库负责保存这些商品向量，并在用户提问时找出语义相近的候选商品；后端再叠加类目、预算、排除词等硬过滤，保证推荐不会越界。
项目支持两套检索配置：Demo 默认可用 local embedding + 本地向量索引，不依赖外部服务；如果要展示真实 RAG 架构，可以切到 Ark embedding + Qdrant 向量数据库。
生成层可以接入 DeepSeek 或 Doubao Ark；没有 Key 时，也有本地确定性回答兜底。
最终通过 SSE 返回流式文本、商品卡片、结构化对比卡和评审模式证据链。
```

屏幕展示：

- `docs/submission/design-document.md` 架构图。
- `server/src/vectordb/embedding.js`、`server/src/vectordb/qdrant.js` 或 `docs/operations/qdrant.md`。
- `server/src/http.js` 或 `docs/reference/architecture.md`。

## 3. 基础推荐

输入：

```text
推荐一款适合油皮的防晒霜
```

讲解词：

```text
这里系统识别到用户想找美妆护肤里的防晒商品，并关注油皮、清爽、控油。
可以看到回答是流式输出的，下方商品卡片和回答里的商品是一一对应的。
点击卡片可以进入详情页，详情里的描述、SKU、FAQ、评价都来自商品数据。
```

重点展示：

- 流式回复。
- 商品卡片。
- 商品详情页。

## 4. 预算追问

输入：

```text
不要超过200
```

讲解词：

```text
这不是一次新搜索，而是对上一轮防晒需求追加预算约束。
后端会继承类目和商品类型，再加入 200 元以内的硬过滤。
所以商品卡片不会继续展示超过预算的商品。
```

重点展示：

- 多轮上下文。
- 预算硬过滤。
- 商品卡片只剩预算内候选。
- 说明：预算限制后防晒候选可能只剩 1 款，因此这一段只展示“硬过滤可信边界”，不要在这条分支后继续做第 2/3 款对比。

## 5. 商品对比和决策

先新开一个会话，或清空当前会话后重新输入：

```text
推荐一款适合油皮的防晒霜
```

输入：

```text
第二款和第三款对比一下
哪个更清爽
```

讲解词：

```text
这里我没有追加 200 元预算限制，因为预算过滤后防晒候选只剩 1 款，无法支撑第 2、3 款对比。
对比问题不会重新从全库搜索。
系统会把“第二款”和“第三款”解析为上一轮候选中的真实商品，并返回结构化对比卡。
后续问“哪个更清爽”时，仍然只在刚才对比过的商品里做决策。
这避免了普通 RAG 项目常见的上下文漂移问题。
```

重点展示：

- 先确保上一轮候选至少有 3 款。
- 对比卡。
- 明确结论。
- 商品 ID 与卡片一致。

## 6. 跨需求记忆

输入：

```text
想买一台办公轻薄笔记本
1万预算
推荐一款适合油皮的防晒霜
刚才笔记本第三款呢
```

讲解词：

```text
同一个会话里可以存在多个购物需求。
系统会把笔记本和防晒拆成两个结构化需求。
当我回问“刚才笔记本第三款”时，它能恢复旧需求，而不是误用当前防晒候选。
```

重点展示：

- 多需求隔离。
- 旧需求恢复。
- 指代解析。

## 7. 边界处理

输入：

```text
天气怎么样
给我点外卖
想买笔记本和防晒霜
```

讲解词：

```text
电商导购 Agent 不能什么都答。
天气和外卖服务不属于商品库导购，所以系统不会触发商品检索，也不会展示无关卡片。
多品类混合输入会先提示拆开聊，避免把两套检索结果揉成一组不可信推荐。
```

重点展示：

- 非导购拒答。
- 无商品卡片。
- 多需求澄清。

## 8. 评审模式证据链

用 `/api/debug/retrieve` 或接口调试工具展示：

```text
推荐一款适合油皮的防晒霜，不要超过200
```

录屏时可以直接在 PowerShell 里执行：

```powershell
$body = @{
  message = "推荐一款适合油皮的防晒霜，不要超过200"
  includeMemory = $false
} | ConvertTo-Json -Compress

$response = Invoke-WebRequest `
  -UseBasicParsing `
  -Uri "http://localhost:3001/api/debug/retrieve" `
  -Method POST `
  -ContentType "application/json; charset=utf-8" `
  -Body ([System.Text.Encoding]::UTF8.GetBytes($body))

$json = $response.Content | ConvertFrom-Json
$json.review | ConvertTo-Json -Depth 8
```

讲解词：

```text
这是项目新加的评审模式。
每次回答都可以看到系统识别的意图、硬过滤条件、候选数量、最终商品证据和安全边界。
这可以证明回答不是模型自由发挥，而是由后端控制商品集合，并且基于商品库字段生成。
普通聊天接口 /api/chat 里也会返回 event: review；当前 Android 不渲染这个事件，所以答辩时用 debug 接口展示更直观。
```

重点展示 `review` 字段：

- `intent`
- `filters`
- `retrieval`
- `evidence`
- `safety`

## 9. 工程质量

讲解词：

```text
工程上，项目提供本地检索和 Qdrant 两种模式，支持模型失败自动降级。
后端有回答、意图、记忆、检索质量、性能、持久化和端到端 smoke 测试。
这保证 Demo 不是只能手动跑一次，而是核心链路可以持续回归验证。
```

屏幕展示：

```text
npm run test:retrieval-quality
npm run test:smoke
```

## 10. 收尾

讲解词：

```text
总结一下，ShopGuide Agent 的重点是可信导购：
第一，回答和卡片严格基于商品数据；
第二，支持多轮记忆、指代和结构化对比决策；
第三，通过评审模式证据链，让 RAG 推荐过程可解释、可验真。
```
