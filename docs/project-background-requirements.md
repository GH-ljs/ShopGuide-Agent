# 项目背景与要求

本文档根据《课题说明会：基于 RAG 的多模态电商智能导购 AI Agent》整理，用于开发过程中统一目标、范围和验收标准。

## 1. 项目背景

本项目面向短视频、直播和内容平台中的电商广告场景，目标是将传统的“展示型广告”升级为“交互型导购”。传统电商广告主要依赖静态图文、短视频或直播内容进行单向展示，用户只能被动浏览，难以及时表达个性化、模糊或长尾需求，最终影响商品理解、购买决策和转化效率。

基于 AI Agent 与 RAG 的智能导购可以通过自然语言对话、多轮追问、商品检索和推荐理由生成，帮助用户从“看到商品”进一步走向“理解商品、比较商品、形成购买决策”。项目重点不是单纯生成回答，而是打通“用户输入 -> 意图理解 -> 商品检索 -> 大模型生成 -> 流式返回 -> 商品卡片展示”的端到端链路。

## 2. 核心目标

- 构建一个基于 RAG 的电商智能导购助手。
- 支持用户用自然语言描述模糊需求，并从商品库中检索和推荐合适商品。
- 支持流式对话体验，降低用户等待感。
- 在回复中展示可点击商品卡片，形成导购与商品落地页之间的连接。
- 严格基于商品数据回答，避免编造不存在的商品、价格、库存、优惠和功能。
- 在完成最小闭环后，逐步增强多轮对话、反选约束、购物车、多模态等能力。

## 3. 典型使用场景

### 3.1 基础场景

- 单轮模糊推荐：例如“推荐一款适合油皮的洗面奶”。
- 条件筛选：例如“200 元以下的蓝牙耳机有哪些？”。

基础场景要求系统能够识别用户意图，抽取类目、预算、功效、适用人群等条件，并从商品库中完成匹配检索。

### 3.2 进阶场景

- 多轮追问与细化：例如“帮我推荐跑鞋” -> “要轻量的” -> “预算 500 以内”。
- 商品对比决策：例如“A 和 B 这两款面霜哪个更保湿？”。
- Agent 主动澄清：当用户只说“推荐一款手机”时，系统应主动询问更看重拍照、续航还是性价比。

进阶场景要求系统具备上下文记忆、需求收敛、候选商品对比和主动澄清能力。

### 3.3 高级场景

- 反选与排除约束：例如“推荐防晒霜，但不要含酒精的，也不要日系品牌”。
- 场景化组合推荐：例如“下周去三亚度假，帮我搭配一套从防晒到穿搭的方案”。
- 购物车与下单：例如“把刚才那款加到购物车”“删掉第二个”“下单吧，地址用默认的”。
- 拍照找货：用户上传图片后，系统识别视觉特征并检索相似商品。

高级场景属于加分方向，重点考察 Agent 对复杂约束、结构化数据操作和多模态输入的处理能力。

## 4. 项目要求

### 4.1 数据工程与特征治理

- 将商品详情、规格、功能、材质、广告文案、用户评价等非结构化内容转化为可检索表示。
- 设计合理的 Chunking 策略，平衡召回率和精确度。
- 保证商品价格、库存、属性等关键字段以结构化数据为准。
- 推荐理由需要能够追溯到商品数据，不能脱离数据源自由发挥。

### 4.2 模型与 Agent 编排

- 建立可靠的 RAG 链路，检索结果不足时应明确说明或主动追问。
- 区分“随便看看”和“明确购买倾向”，并使用不同推荐策略。
- 通过 Prompt Engineering 控制回答结构、语气、商品卡片字段和安全边界。
- 对模型输出进行必要约束，禁止编造优惠券、库存、价格和商品功能。

### 4.3 后端服务化

- 后端可使用 Python、Go 或 Node.js 实现。
- 需要集成向量数据库或等价的向量检索能力。
- 提供流式 API，优先支持 SSE 或 WebSocket。
- 设计清晰的检索、生成、商品结构化返回和错误处理流程。
- 考虑超时、降级、并发和服务稳定性。

### 4.4 客户端工程与体验

- 客户端必须是 iOS 或 Android 原生 App，不接受纯 Web/H5 方案替代。
- 支持对话窗口和文字输入。
- 支持 AI 回复的逐字或分片流式渲染。
- 支持在对话流中展示商品卡片，并可点击跳转落地页或详情页。
- 加分方向包括语音输入、TTS 语音播报、拍照找货、流畅动效和富交互商品卡片。

## 5. 最小闭环交付标准

项目应优先完成最小可演示闭环，再继续扩展能力。

### 5.1 数据与资源

- 使用导师提供或自主采集的 50-100 条脱敏电商商品数据。
- 商品字段至少包含商品名、类目、价格、详情描述和主图 URL。
- 模型 API Key 属于敏感信息，应通过环境变量或本地配置使用，不应写入仓库文档或源码。

### 5.2 客户端

- iOS 或 Android 原生 App。
- 支持发送文本消息。
- 支持接收并渲染 AI 流式回复。
- 支持展示可点击商品卡片。

### 5.3 后端

- 实现 RAG 基本链路。
- 集成商品检索能力。
- 提供 SSE 或 WebSocket 流式接口。
- 返回结构化商品卡片数据，便于客户端展示。

### 5.4 模型能力

- 能理解模糊需求，例如“推荐护肤品”。
- 能从库内商品中检索候选结果。
- 能给出简洁、合理、基于数据的推荐理由。
- 不能编造虚假商品、价格、优惠或功能。

## 6. 加分方向

### 6.1 购物车与下单能力

- 对话式加购：用户说“把这个加到购物车”时，系统能识别并执行加购。
- 购物车管理：支持删除、改数量等自然语言操作。
- 下单确认流程：模拟地址确认、订单汇总和下单闭环。

### 6.2 多模态交互能力

- 语音输入：端侧 ASR 后进入正常 RAG 流程。
- TTS 播报：将 AI 回复朗读出来。
- 拍照找货：结合图像理解和相似商品检索。

### 6.3 对话智能与 RAG 增强

- 多轮上下文记忆。
- 反选和排除条件解析。
- 多商品结构化对比。

### 6.4 工程质量与性能优化

- 热门查询缓存，降低重复模型调用成本。
- 优化首 Token 延迟，目标体验接近实时对话。
- 打磨客户端动效、骨架屏、商品卡片交互和异常状态体验。

## 7. 提交与评审重点

### 7.1 交付材料

- 可运行 Demo：包含客户端 App 和后端服务，建议准备 3-5 分钟演示。
- 源代码仓库：结构清晰、注释规范、README 可运行。
- 技术文档：包含架构设计、接口设计和关键方案说明。

### 7.2 代码规范

- 前后端代码分目录，例如 `/client`、`/server`、`/docs`。
- 明确依赖项和版本，例如 `package.json`、`requirements.txt`、`Podfile` 等。
- 对 RAG 链路、Prompt 构造、检索过滤、商品卡片结构化等核心逻辑添加清晰注释。

### 7.3 评分维度

- 基础功能完整性：端到端链路是否跑通。
- 工程质量：代码结构、接口设计、错误处理和文档质量。
- 效果与可靠性：检索准确性、无幻觉输出、运行流畅度和 UI 体验。
- 加分项深度：多模态、性能优化、购物车闭环或交互创新是否真正做深。

### 7.4 明确减分项

- AI 编造不存在的商品、价格、优惠信息。
- 用纯 Web/H5 替代原生 App。
- Demo 无法正常运行或依赖大量手动配置。
- 代码无法解释实现原理或关键链路。

## 8. 当前仓库落地方向

当前仓库已经按 `/server`、`/client`、`/docs` 分层组织。后续开发建议按以下顺序推进：

1. 继续完善后端 RAG 检索和结构化商品返回。
2. 接入向量数据库与真实 Embedding。
3. 强化多轮上下文、否定条件和商品对比。
4. 创建 Android 或 iOS 原生客户端。
5. 实现客户端流式渲染和商品卡片展示。
6. 在基础闭环稳定后，选择 1-2 个加分项深入实现。
