客户端与后端如何连接

客户端不直接碰模型，也不自己检索商品。它只负责收集用户输入、发请求、消费后端返回的 SSE 事件并更新 UI。

Android 客户端
ChatScreen.kt 用户输入、消息列表、loading 状态、conversationId。
send message ->
ChatApi.kt POST /api/chat，并逐行读取 text/event-stream。
<- token / products / done
MessageBubble.kt + ProductCardView.kt 文本逐步增长，商品卡片在 products 事件到达后展示。
HTTP 协议层
server/src/http.js 所有 API 路由都从这里进入。/api/chat 是最小闭环核心。
writeSse("token")
SSE 响应 后端保持连接，先发文本 token，再发商品 products，最后发 done。
错误时 writeSse("error")
错误统一格式 buildError 让客户端能稳定识别错误类型。
后端内部和外部服务
memory.js + retriever.js 把自然语言变成检索条件，再从商品库里找候选。
候选商品 ->
answer.js + llm.js 构造 Prompt，调用 Ark 或 DeepSeek；没 Key 时走本地兜底回答。
可选 ->
local 向量 / Qdrant / Ark Embedding 负责“相似商品排序”，但商品事实仍来自本地商品 JSON。
关键理解：客户端只相信 products 事件里的结构化商品卡片，不从模型自然语言里解析商品。 本地调试：Android 模拟器访问宿主机后端通常使用 10.0.2.2:3001。

后端 RAG 链路

RAG 可以简单理解为：先从可信商品数据里“找资料”，再让模型基于这些资料“组织语言”。这个项目把“找”和“说”分开，降低幻觉风险。

1

启动时准备商品库

index.js 读取配置，调用 loader.js 加载 JSON 商品，并创建向量检索器。

2

收到 /api/chat

http.js 校验 message，打开 SSE 头，拿到 conversationId 对应的会话。

3

更新多轮状态

memory.js 从本轮输入里提取类目、预算、偏好、排除词，保存在 state 中。

4

构造检索 Query

把最近对话、结构化状态、上一轮商品摘要和当前问题拼成检索文本，支持“再便宜点”这类追问。

5

硬过滤候选商品

retriever.js 先按类目、商品类型、价格、否定词过滤，确保结果符合硬条件。

6

向量相似度排序

local.js 或 qdrant.js 在候选范围内做相似度排序，选出 topK。

7

生成回答文本

answer.js 生成本地兜底回答或模型 messages，llm.js 调用模型流式返回 token。

8

返回商品卡片

文本 token 发送完后，后端发送 products 事件。客户端用它渲染可点击商品卡片。

客户端和后端的接口契约

接口契约就是双方约好的“语言”。后端保证按这个格式返回，客户端就能稳定渲染。

请求：POST /api/chat

客户端每发一轮消息，都带上同一个 conversationId，让后端复用多轮会话状态。

{
  "conversationId": "demo-user-1",
  "message": "推荐一款适合油皮的洗面奶"
}

响应：text/event-stream

这是一个长连接响应。每个事件由 event 和 data 组成，空行表示一个事件结束。

event: token
data: {"content":"根据你的需求，"}

event: products
data: {"products":[{"productId":"p_beauty_011","title":"..."}]}

event: done
data: {"ok":true,"conversationId":"demo-user-1"}

商品卡片字段

客户端渲染商品卡片只看 products 事件，不从模型回答文本里提取商品名或价格。

{
  productId,
  title,
  brand,
  category,
  subCategory,
  price,
  imageUrl,
  reason
}

调试：POST /api/debug/retrieve

当你想知道“为什么推荐这个商品”时，看这个接口最直观。

{
  parsed: { category, itemIntent, maxPrice, negativeTerms },
  counts: { totalProducts, filteredCandidates, finalProducts },
  vectorMatches: [{ productId, title, score }],
  products: [...]
}

用后端开发思维理解这个项目

1. 先看数据流，不先看语法

后端代码的核心不是某个语法点，而是一次请求经过哪些模块、数据形状怎么变化、哪里可能失败。

  • 输入：用户自然语言 message。
  • 中间态：session state、retrievalQuery、matchedProducts。
  • 输出：SSE token、products、done 或 error。

2. 分层是为了控制复杂度

如果把所有逻辑写在 http.js，短期能跑，长期很难改。现在的分层让每个文件只关心一种问题。

  • http.js 关心协议和路由。
  • retriever.js 关心怎么找商品。
  • answer.js 关心怎么组织回答和卡片。
  • vectordb 关心检索底层实现。

3. RAG 的关键是可信边界

模型很会说话，但不能让它决定事实。商品、价格、图片、SKU 应该来自商品库。

  • 模型只基于候选商品上下文回答。
  • 商品卡片由后端结构化生成。
  • Prompt 和本地兜底都强调不编造优惠、库存和价格。

4. 流式接口是在改善体验

SSE 让用户不用等整段模型回答结束。后端一点点推 token，客户端一点点渲染。

  • token 事件更新文本。
  • products 事件更新卡片。
  • done 事件关闭 loading。
  • error 事件给出可展示错误。

建议阅读顺序

先读 http.js 看 /api/chat 怎么串起整个请求。不要一开始陷进细节。
再读 memory.js 理解多轮会话为什么需要 state，不只是保存聊天记录。
然后读 retriever.js 重点看硬过滤和向量排序如何配合，理解推荐结果从哪里来。
接着读 answer.js 看商品卡片和 Prompt 如何保证回答基于数据。
最后读 vectordb 先理解 local.js，再看 qdrant.js。底层可替换，上层接口不变。

一眼看懂最小闭环

客户端 ChatScreen
  -> ChatApi.streamChat(message, conversationId)
  -> POST http://10.0.2.2:3001/api/chat
  -> server/src/http.js handleChat
  -> memory.js 更新会话状态
  -> retriever.js 检索商品
  -> vectordb/local.js 或 qdrant.js 排序
  -> answer.js 构造回答和商品卡片
  -> llm.js 流式模型生成，或者 buildLocalAnswer 本地兜底
  -> SSE event: token
  -> SSE event: products
  -> SSE event: done
  -> 客户端更新文本和商品卡片
